# 工作流后端面试题参考答案

> 对应《工作流开发与设计面试题库》中的后端题目：第二章到第六章，以及第八章的场景设计题。每题先给结论，再展开关键点；面试时先讲核心方案，再补充边界和取舍。

## 答题原则

- 结论先行：先说出你会怎么做，再解释为什么。
- 给结构：数据模型、接口、状态机、队列拓扑比背概念更有说服力。
- 主动说失败场景：超时、重试、重复投递、部分失败是工作流面试的加分点。
- 结合项目：可以用 MeowFlow、扣子（Coze）、Dify 里的节点和执行机制举例。

## 二、节点与编排能力题

### 1. 工作流节点通常分为哪几类？节点如何抽象？

按能力分为触发器、AI、逻辑控制、数据处理、集成、通知和人工节点。抽象一个节点至少要包含：

- 固定 ID 和类型。
- 配置 Schema：节点配置如何填写和校验。
- 输入 Schema 和输出 Schema：上游结果如何进入、结果如何被下游引用。
- 执行器：接收配置、输入和上下文，返回标准化输出或错误。
- 元信息：是否产生副作用、是否可重试、是否允许并行。

所有节点输出统一为 JSON 或标准对象，这样下游、画布和日志才能用同一套规则处理。

### 2. 条件分支如何设计？

条件节点配置一组表达式，例如 `[{left, op, right}]`，支持 `and/or/not` 组合。执行时对表达式求值，命中哪个分支就走哪个出口，都不命中就走默认分支。关键点：

- 表达式必须空值安全，字段不存在时按配置返回 false、true 或报错。
- 保存时校验引用路径，运行时报错要能定位到节点和条件。
- 分支出口用 edge 的 sourceHandle 表达，前端画布和后端模型保持一致。
- 禁止直接拼接用户输入执行任意代码。

### 3. 并行分支（Fork/Join）如何实现？

Fork 节点把执行拆成多个分支任务，每个分支持有独立但可共享父级上下文的数据区。Join 节点等待依赖全部分支完成，再按策略合并：

- 全部成功才继续。
- 任一成功即继续。
- 失败不阻塞其他分支，只把错误汇总。

分支任务要有独立的任务 ID，Join 节点维护“已到达分支数”和“分支总数”，到达后触发下游。还要配置 Join 超时，防止分支永久挂起。

### 4. 循环和遍历节点如何设计？

遍历节点接收一个数组，每次迭代产生子上下文，例如 `loop.item`、`loop.index`、`loop.all`。配置包括最大迭代数、批次大小、并发度和失败策略。

Map 场景中，每次迭代执行同一段子流程，结果按顺序写入结果数组。每个迭代要有持久化进度，失败时可以定位到第几个元素，支持跳过、停止或重试。必须设置最大迭代数和总执行时间上限，防止失控。

### 5. 子流程如何设计？

子流程节点引用一个工作流定义 ID 和版本 ID，配置输入映射和输出映射。执行时：

- 通过引用路径把父级数据映射到子流程输入。
- 子流程结束后把结果映射回父级上下文。
- 子流程使用独立的变量空间，但共享 traceId。
- 版本要固定，避免发布新版本后旧流程行为变化。
- 限制嵌套深度和循环调用，防止递归死循环。

### 6. 人工审批、暂停、等待回调节点怎么实现？

节点执行到人工步骤时把实例状态置为 WAITING，并创建审批任务记录：runId、nodeId、审批人、截止时间、状态、动作和审批意见。

- 审批通过后恢复执行并写入审批结果。
- 拒绝时走拒绝分支。
- 超时由定时任务扫描，自动升级、提醒或按配置拒绝。
- 支持第三方系统通过回调接口异步更新审批结果，回调要验签并幂等。
- 审批过程全部留痕，供审计查询。

### 7. 多种触发器如何设计？

触发器是可执行入口，统一暴露触发元数据：

- Webhook：生成唯一入口，校验签名，对请求 ID 做幂等，同步确认接收、异步执行。
- 定时：解析 cron，支持时区，补跑策略要明确，集群下用分布式锁避免重复触发。
- 表单或消息：把事件载荷映射成工作流输入后启动执行。
- 消息队列触发：消费消息后启动，消费逻辑要幂等。

触发器只负责“入站”，后续逻辑统一交给执行引擎。

### 8. 节点之间的数据如何传递？

核心是上下文对象，保存工作流输入、全局变量和节点输出。结构类似：

```text
context = {
  runId, workflowId, versionId,
  inputs, outputs: { nodeId: JsonNode },
  loop: { item, index, all }
}
```

下游通过 `nodeId.output.field` 或 `loop.item` 引用。作用域分流程级、节点级、循环迭代级。文件和大对象只存引用，不把内容直接放进上下文。所有写入都要做大小限制。

### 9. 表达式语言如何设计？

使用受限表达式语言，而不是直接执行代码：

- 解析为 AST，只支持字段引用、比较、逻辑运算、算术和内置函数。
- 函数白名单管理，禁止文件、网络、系统命令等能力。
- 执行时限制节点数和耗时。
- 保存时做静态校验，运行时错误带清晰路径。
- 可选做法是复用现成表达式库，但必须关闭危险能力。

### 10. 动态节点和静态编排如何共存？

动态能力仍然建立在固定节点模型上：AI 生成工作流、动态选择工具时，最终产物必须是一个合法的工作流 JSON，并经过和手工编辑相同的校验流程。

- 动态节点输出不确定时，运行时用通用 JSON 表示，Schema 允许 object 或 any。
- AI 选择工具时，工具列表来自注册中心，不能凭空调用。
- 未知节点类型、未知工具、非法引用都要在保存或执行前拦截。

## 三、执行引擎与并发题

### 1. 工作流执行引擎的核心职责是什么？

执行引擎负责加载定义、校验 DAG、调度就绪节点、调用节点执行器、持久化状态、处理重试和取消、收集日志和 Trace，并对外返回执行状态。

引擎不应该硬编码业务节点逻辑，而是通过节点注册中心驱动；它只关心“何时执行谁”和“结果如何流转”。

### 2. 如何判断一个节点可以开始执行？

构建 DAG 时为每个节点计算入度（依赖数），执行时维护就绪计数：

- 入度为 0 的起始节点直接进入就绪队列。
- 节点完成后减少所有下游节点的就绪计数。
- 计数变为 0 时投递该节点任务。

这种方式天然支持并行，也不会重复唤醒同一节点。

### 3. DAG 拓扑排序和判环怎么做？

常用 Kahn 算法：统计入度，把入度为 0 的节点入队，出队时减少下游入度。如果最终处理的节点数小于总节点数，说明存在环。

也可以用 DFS 三色标记检测环。判环必须在保存、发布和执行器加载定义三个入口都做，防止脏定义直接进入执行。

### 4. 节点完成后如何只唤醒就绪的下游？

节点完成事件携带 runId、nodeId、结果和状态。调度器根据 edges 找到下游，更新就绪计数并写回持久化状态，计数归零后生成新任务。

为避免重复投递，节点实例状态使用唯一约束或状态机 CAS，同一个下游任务只允许被创建一次。

### 5. 并行节点用什么并发模型？

推荐“有界线程池 + 异步任务队列”：

- 每个节点任务是独立任务对象，由调度器投递。
- 计算型节点使用固定线程池。
- LLM、HTTP 等 IO 型节点使用异步客户端或独立 IO 池，避免占满计算线程。
- Java 21 下可以用虚拟线程简化阻塞调用，但仍要限制总并发数。

不要为每个节点直接 new 线程，也不要在一个同步请求里跑完整张图。

### 6. 动态并行如何控制并发度？

把列表切分成批次，每个批次是一个可调度的任务，配合全局信号量限制并发：

- 每批条数、最大并发、失败策略可配置。
- 每批执行结果持久化，支持进度查询。
- 失败支持“跳过继续”“整批重试”“立即停止”三种策略。
- 设置总批次数和总执行时间上限，防止数据量失控。

### 7. 节点超时和取消如何实现？

节点执行时使用超时包装，到时间后标记失败或超时状态，并触发取消：

- 取消令牌传递给节点执行器，HTTP 请求、LLM 调用、子流程都要响应取消。
- 父节点取消时要级联取消子节点或并行分支。
- 正在运行的节点要能被扫描任务接管，防止进程重启后卡在 RUNNING。
- 超时与重试组合：超时通常属于可重试错误，但要限制总次数。

### 8. 节点失败重试策略怎么设计？

先对错误分类：

- 瞬态错误：网络超时、5xx、限流，可重试。
- 永久错误：参数校验失败、非法配置，不重试。
- 副作用风险：必须幂等后才能重试。

重试参数包括最大次数、初始间隔、指数退避、随机抖动和最大重试窗口。超过次数进入死信队列，等待人工或定时补偿。

### 9. 执行状态如何持久化？如何支持中断恢复？

使用执行实例表和节点实例表：

```text
workflow_run: id, workflow_id, version_id, status, created_at, finished_at
node_instance: id, run_id, node_id, status, input, output, error, started_at, finished_at
```

状态机为 PENDING、RUNNING、SUCCEEDED、FAILED、WAITING、CANCELLED。恢复时扫描长时间停留在 RUNNING 但心跳过期的节点，重新调度或标记失败。

### 10. 如何防止死循环、超大 DAG 和资源耗尽？

- 定义阶段做 DAG 判环。
- 循环节点限制最大迭代数。
- 限制总节点数、边数、嵌套深度、单次运行总时长。
- 执行时限制并行度、内存和外部调用频率。
- 提供强制取消入口，取消后级联清理子任务。

### 11. 一次执行可能被调度多次，如何保证幂等？

每个任务使用全局唯一 ID：runId + nodeId + attempt。消费侧先用数据库唯一约束或 Redis SETNX 抢占，成功后再执行；执行结果用 CAS 更新状态，避免旧任务覆盖新状态。

外部副作用同样携带幂等键，依赖外部系统去重；外部系统不支持时，采用“先查后写”或事务性 outbox。

### 12. 如何设计可横向扩容的执行引擎？

拆成“调度器”和“执行器”：

- 调度器负责解析 DAG、生成可执行任务。
- 执行器从持久化队列消费任务，执行后回写结果。
- 节点任务带租约和心跳，执行器崩溃后可被回收。
- 数据库是最终状态源，队列负责异步分发。
- 消费端按 runId 或节点类型分区，避免乱序。
- 新增执行器即可扩容，监控队列积压和执行耗时。

## 四、数据、上下文与 Schema 题

### 1. 工作流上下文应该保存哪些信息？

上下文保存运行标识、工作流定义、输入、变量、节点输出、Trace、环境和取消令牌：

```text
{
  runId, workflowId, versionId, tenantId, userId,
  inputs, outputs, env, traceId, cancelFlag
}
```

大对象不放入上下文，改为引用 ID、URL 或存储位置。

### 2. 节点输出引用路径如何解析？

定义引用语法，例如 `node_id.output.field[0]`。解析器把路径拆成节点 ID、output、字段和数组下标，在上下文中逐级查找。

引用不存在时按配置返回 null、报错或走默认值。保存时可以做静态引用校验，运行时报错要带完整路径。

### 3. 工作流变量需要支持哪些类型？

至少支持 JSON 类型：字符串、数字、布尔、数组、对象、null，以及平台特有的文件、图片、日期和选择项。

文件、图片存引用而不是二进制内容；选择项在 Schema 中定义枚举。运行时统一用 JsonNode 承载，节点输出前做类型校验和大小限制。

### 4. 节点输出 Schema 校验怎么做？

保存节点配置时校验配置 Schema，运行时校验输入和输出 Schema。可以复用 JSON Schema：

- 必填字段、类型、枚举、嵌套结构。
- 数值范围、字符串长度、数组最大长度。
- 类型转换只做安全转换，例如字符串数字转数字，不允许隐式地把对象当字符串。

校验失败的错误信息要包含节点 ID、字段路径和期望类型。

### 5. 敏感信息如何加密和脱敏？

- API Key、密码等配置字段加密存储，前端回显时只显示掩码。
- 执行日志不打印完整密钥，输入输出日志支持字段级脱敏。
- 数据库字段用加密类型处理器，例如 MyBatis 自定义 TypeHandler。
- 查看执行详情要做权限校验，密钥类配置不随执行详情返回。

### 6. 大模型节点的大段输出如何处理？

避免把全部内容塞进上下文：

- 内容落 PostgreSQL 或对象存储，上下文只保存引用和元数据。
- 设置单节点输出大小上限，超出后截断、分页或摘要。
- LLM 节点的 context 在送入 prompt 前按 Token 预算裁剪。
- 定期清理过期的大对象和旧执行结果。

### 7. prompt 模板中的变量替换怎么做？

使用严格模板语法，例如 `{{node_id.output.field}}`：

- 模板先编译，运行时解析引用路径取值。
- 变量缺失或类型不对时给出明确错误。
- 值进入 prompt 前做转义和长度限制。
- 支持变量预览和 Token 估算，方便用户在保存前检查。

### 8. 表达式求值如何保证安全？

- 使用 AST 解析，不调用 eval。
- 只允许白名单函数，禁止文件、网络、系统命令。
- 限制表达式大小、执行耗时和递归深度。
- 字段引用限定在当前上下文，不暴露内部对象。
- 必要时在独立沙箱或受限 ClassLoader 中执行。

### 9. Schema 变更后，存量工作流和执行中实例如何处理？

工作流定义按版本不可变保存，执行实例绑定发布时的版本快照：

- 旧版本继续运行，不被新版本影响。
- 发布新版前做兼容性检查，例如移除必填字段属于破坏性变更。
- 执行中的实例按原版本完成，新实例按新版本执行。
- 回滚时发布历史版本即可。

### 10. 如何设计对画布友好的工作流 JSON？

核心结构：

```json
{
  "schemaVersion": 1,
  "startNodeId": "start_1",
  "nodes": [
    { "id": "start_1", "type": "start", "config": {} }
  ],
  "edges": [
    { "source": "start_1", "target": "llm_1", "sourceHandle": "success" }
  ]
}
```

节点 ID 保持稳定，字段支持向后兼容扩展；画布和引擎共用同一份 Schema，避免前端能保存、后端不能执行。

## 五、可靠性、一致性与监控题

### 1. 工作流执行失败后，用户应该看到什么？

用户需要看到运行状态、失败节点、错误原因、失败节点的输入输出摘要，以及重试或重新运行入口。完整日志和技术细节放在详情页，不要堆在列表里。

日志必须包含 runId、nodeId，并且敏感信息脱敏。

### 2. Trace ID 如何贯穿整个链路？

入口生成 traceId，通过 HTTP Header 和 MQ Message Header 传递到各服务。工作流、节点、外部调用和数据库操作都记录同一 traceId，并附加 runId、nodeId。

查询时按 traceId 聚合一次运行的完整链路，按 runId 查看节点级明细。

### 3. 节点产生副作用后失败，重试如何避免重复？

执行副作用前生成幂等键，例如 `runId:nodeId:attempt`，调用外部系统时放在请求头或请求体中；外部系统按幂等键去重。

外部系统不支持幂等时，用事务性 outbox：本地事务写业务状态和待发送消息，发送成功后再标记，失败后扫描重发。也可在重试前查询外部结果，已成功则直接返回成功。

### 4. at-least-once 和 exactly-once 如何权衡？

消息队列通常只能保证 at-least-once，重复消费由业务幂等解决。exactly-once 需要事务消息、唯一键和状态机配合，成本高。

工作流任务推荐 at-least-once + 幂等消费：消息可以重复，但节点结果不能重复写入。

### 5. RabbitMQ 和 Kafka 如何选择？

RabbitMQ 更适合任务队列：消息确认、死信、延迟队列、按路由分发。Kafka 更适合事件流：高吞吐、分区、消费位点、历史回放。

工作流任务投递用 RabbitMQ 或类似任务队列；审计、行为事件、统计流可以用 Kafka。

### 6. 死信、重试、延迟队列如何设计？

以 RabbitMQ 为例：

- 主队列消费失败时把消息转到重试队列。
- 重试队列带 TTL 和路由键，到期后回到主队列，消息头记录重试次数。
- 超过最大重试次数转到死信队列，由监控或人工处理。
- 延迟执行、超时提醒使用延迟消息，例如 RabbitMQ Delayed Message Plugin。

### 7. 数据库事务边界应该画在哪里？

本地事务只包住状态更新和 outbox 写入，不要在事务里调用 LLM 或外部 HTTP。外部调用成功后通过独立事务更新节点状态。

如果跨多个服务，使用状态机推进或 Saga 模式；不要用长事务锁住执行实例。

### 8. 多个执行器消费同一个任务，如何保证只执行一次？

- 任务 ID 在节点实例表上建唯一约束，先插入后执行。
- 执行前用 Redis SETNX 抢占执行权并带租约时间。
- 更新状态用 CAS：只有 RUNNING 才能变为 SUCCEEDED。
- 执行器心跳过期后任务才允许被重新接管。

### 9. 如何做补偿？

先按错误分类：

- 瞬态错误自动重试。
- 已经产生副作用但确认失败的，走补偿流程，例如撤销订单、退费、标记失败。
- 无法自动补偿的进入人工处理队列，并保留完整审计。

补偿动作本身要幂等，避免重复补偿。

### 10. 监控、告警和成本统计怎么做？

指标至少包括运行量、成功率、平均耗时、P95、队列积压、节点失败数、重试次数、模型 Token 和费用。按工作流、用户、团队、模型供应商维度聚合。

告警关注成功率下降、队列积压、超时比例升高、成本突增。成本在节点结束时记录用量，实时统计用 Redis 累加，最终落库。

### 11. 限流、熔断、降级如何设计？

- 租户、用户、节点类型、模型供应商分别设限流。
- 外部依赖使用熔断器，失败率或慢调用比例超过阈值后快速失败。
- 模型供应商支持 fallback 列表，主供应商不可用时切备用。
- 执行队列积压过高时拒绝新运行或降级为排队，避免拖垮平台。

## 六、架构与扩展题

### 1. 一个类 Dify 工作流平台通常包含哪些模块？

- 网关与认证：登录、权限、路由。
- 工作流模块：定义、版本、发布、校验。
- 执行引擎：DAG 调度、节点执行、状态持久化。
- 节点注册中心：内置节点和插件节点。
- 触发器：Webhook、定时、表单、消息。
- 模板市场：模板分类、搜索、使用统计。
- 监控模块：执行日志、指标、告警、成本。
- 基础设施：PostgreSQL、Redis、RabbitMQ、对象存储。

### 2. 工作流定义、版本、执行实例、节点实例之间是什么关系？

- 工作流 1 对 N 版本。
- 每次运行绑定一个版本快照。
- 一次运行 1 对 N 节点实例。
- 模板本质上是可复用的工作流定义，带分类、评分、使用量等市场属性。

版本不可变，执行不跟随最新定义变化。

### 3. 节点执行器如何做成插件化？

定义 NodeExecutor 接口，注册中心维护 type 到执行器工厂的映射：

- SPI、注解扫描或 JAR 包加载。
- 每个插件声明节点类型、分类、配置 Schema 和权限。
- 插件输出标准化 JSON。
- 平台插件可动态启用、停用和灰度，但不能绕过校验直接执行。

### 4. 如何接入 MCP、HTTP 工具、内置工具？

统一抽象为“工具”：名称、参数 Schema、认证方式、调用方式和结果格式。

- MCP 通过工具适配器连接 MCP Server，做连接复用、超时和鉴权。
- HTTP 工具按 OpenAPI 或自定义描述生成请求。
- 内置工具直接调用本地服务。
- 调用结果统一转为 JSON 写回上下文，失败信息也要结构化。

### 5. 模型供应商如何统一抽象？

定义 ModelProvider 接口，包含模型列表、chat、embedding、用量统计。供应商实现各自的客户端，平台层负责：

- 统一模型 ID 和参数映射。
- 路由：按配置、健康状态、价格、优先级选择。
- fallback：主供应商失败时切备用。
- 熔断和限流：保护平台不被单个供应商拖垮。
- 用量上报：Token、耗时、费用。

### 6. 为什么把 workflow、executor、monitor 拆成独立服务？

好处是职责清晰、独立扩容、独立发布和故障隔离。坏处是分布式一致性问题、调用链变长、运维复杂度上升。

建议用事件驱动解耦：workflow 服务发布执行计划，executor 消费执行，monitor 订阅事件。小规模阶段可以先合并，规模上来再拆。

### 7. Redis、PostgreSQL、RabbitMQ 分别承担什么职责？

- PostgreSQL：工作流定义、版本、运行实例、节点实例、日志和费用的最终存储。
- Redis：缓存、分布式锁、限流、短暂状态、热点数据。
- RabbitMQ：异步任务投递、重试、延迟执行和事件通知。

原则是：最终一致性数据放数据库，瞬时状态放 Redis，异步流转放 MQ。

### 8. 执行器如何水平扩容？

执行器做成无状态 worker，从队列消费任务，状态全部读写数据库：

- 节点任务带租约和心跳，崩溃后可回收。
- 同一 run 的顺序性通过分区或状态机保证。
- 消费幂等，避免重复执行。
- 扩容只需增加 worker 实例，缩容前等待队列排空或主动迁移租约。

### 9. 多租户资源配额如何设计？

配额服务按租户维护模型调用、并发、存储和月度预算：

- 执行前预占配额，执行后释放或结算。
- 超配额时拒绝新运行或进入队列。
- 模型调用按 Token 和费用实时扣减。
- 配额校验放在网关和执行引擎两层，避免绕过入口。

### 10. 如何实现工作流灰度发布？

发布时创建新版本并绑定发布规则：

- 按租户、用户组、百分比路由。
- 执行时按规则选择版本，而不是永远用最新版本。
- 已开始运行的实例继续用旧版本。
- 监控新版本成功率，异常时修改规则回滚，不需要重新部署。

### 11. 自研引擎和成熟引擎如何权衡？

- Temporal：适合需要持久化执行、重试、长任务恢复的场景。
- Camunda：适合 BPMN、人工任务、合规要求强的场景。
- n8n/Zapier：适合低代码集成，扩展能力受平台限制。
- 自研：适合 AI 节点多、控制力要求高、需要深度定制画布和成本的平台。

关键看团队规模、交付时间和业务对灵活性的要求；不要为了“自研”而自研。

## 八、场景与设计题

### 1. 请假审批工作流

数据模型包含流程实例、审批任务、审批记录。状态机为 SUBMITTED -> APPROVING -> APPROVED / REJECTED。

- 一级审批人审批后判断是否进入二级。
- 支持抄送、撤回、转办、会签。
- 超时由定时任务扫描，自动提醒、升级或拒绝。
- 每次审批记录操作人、意见和时间，完整审计。

### 2. RAG 工作流

节点链：输入节点 -> 知识库检索 -> LLM 生成 -> 发送邮件。每个节点的输出契约要明确：

- 检索节点输出 `{hits, context}`。
- LLM 节点输出 `{answer, tokens}`。
- 邮件节点输出发送状态。

失败点包括输入为空、检索无结果、context 超过 Token 预算、邮件服务超时。每个点都要有默认值和错误策略。

### 3. 用自然语言生成工作流

由 LLM 输出结构化工作流 JSON，后端做完整校验：

- 节点类型必须来自注册中心。
- 节点 ID、edge 引用必须存在。
- 不能出现环、孤立节点、必填配置缺失。
- 校验失败时把错误反馈给 LLM 修复，或转人工编辑。

生成结果只作为草稿，发布前由用户确认，执行仍然走统一引擎。

### 4. 10 万条数据批量处理

不要一次加载 10 万条，也不要一条一条调度：

- 分批读取，每批 100 到 1000 条。
- 每个批次一个任务，配合有界并发。
- 批次级 checkpoint，支持断点续跑。
- 失败批次自动重试，超过次数进死信。
- 每条或每批记录处理状态，方便进度和失败定位。
- 预算、Token、并发都要设上限。

### 5. 固定工作流和多智能体如何统一？

把 Agent 本身抽象成一种节点类型：

- Agent 节点有自己的输入输出和循环上限。
- 工作流负责外层控制，Agent 负责内层推理。
- 统一上下文和 Trace，Agent 的中间思考也写入日志。
- 用户在画布上决定哪一步交给 Agent，哪一步用固定逻辑。

### 6. 传统 BPMN 迁移到 DAG 工作流

- userTask 映射为人工审批节点。
- exclusiveGateway 映射为条件分支。
- parallelGateway 映射为 Fork/Join。
- 循环结构映射为循环节点。
- timer event 映射为定时触发或延迟节点。
- event 和消息映射为对应触发器。

迁移时保留原流程的权限、时限和审计要求。

### 7. 模板市场

模板是工作流定义加市场属性：

- 基础表：模板、版本、分类、标签。
- 市场表：评分、评价、使用量、上架状态。
- 使用量用异步计数，避免每次使用都写热点行。
- 搜索支持分类、标签、标题和评分排序。
- 上架前人工或规则审核，修改后走版本发布。

### 8. 团队权限体系

采用 RBAC 加资源所有权：

- 角色：成员、编辑者、测试者、发布者、管理员。
- 资源按工作区或团队归属。
- 动作包括查看、编辑、测试、发布、删除、查看日志。
- 权限在 API 层和服务层双重校验，操作写审计日志。

### 9. 第三方回调的异步审批节点

节点进入 WAITING 时创建回调令牌，第三方审批完成后请求回调接口：

- 校验签名或令牌。
- 根据外部订单号定位等待中的节点。
- 更新审批结果并恢复执行。
- 回调重复时幂等处理。
- 超时未回调由定时任务处理，可轮询第三方或人工介入。

### 10. 可视化 + AI 生成 + 手工微调如何共存？

三者共用同一份工作流 JSON 和校验规则：

- AI 生成的是草稿，可以继续手工编辑。
- 画布编辑和 AI 修改都通过版本管理保留差异。
- 发布前强制校验，执行时再次校验。
- 关键决策保留人工确认，避免 AI 直接改动线上流程。
