## 二、技术栈汇总

### 2.1 核心技术栈

| 层级 | 技术 | 版本 | 用途 |
|------|------|------|------|
| **语言** | Java | 17+ | 后端开发语言 |
| **框架** | Spring Boot | 3.x | 应用框架 |
| **ORM** | MyBatis-Plus | 3.5+ | 数据库访问 |
| **数据库** | PostgreSQL | 15+ | 主数据库 + 日志存储 |
| **缓存** | Redis | 7+ | 会话、锁、限流 |
| **消息队列** | RabbitMQ | 3.12 | 异步任务 |
| **对象存储** | MinIO | - | 文件存储 |
| **限流熔断** | Resilience4j | 2.x | 限流熔断 |
| **上下文透传** | Alibaba TTL | 4.x | 线程上下文 |
| **认证** | Sa-Token | 1.37+ | 认证授权 |

> 📌 **日志存储说明**：本系统所有日志（包括业务执行日志、链路追踪、监控告警、错误日志）统一存储到 PostgreSQL，利用 JSONB + GIN 索引 + 全文检索（pg_trgm/zhparser）实现类似 ES 的检索能力。这样可以保证日志与业务数据的事务一致性，降低架构复杂度。等数据量增长到需要专用搜索引擎时再考虑引入 ES。
> 📌 **数据一致性测试**：每个技术组件都有对应的数据一致性风险点，详见 [`DATA_CONSISTENCY_TEST.md`](../test/DATA_CONSISTENCY_TEST.md) 和 [`CROSS_REFERENCE.md`](../test/CROSS_REFERENCE.md)

### 2.2 各模块技术栈

| 模块 | 依赖技术 | 核心功能 |
|------|---------|---------|
| **MeowFlow-common** | Spring Boot, Resilience4j, TTL | 线程池、限流熔断、链路追踪、上下文透传 |
| **MeowFlow-infra** | OpenAI SDK, Spring AI | ChatClient 抽象、模型路由、多路检索、MCP |

| **MeowFlow-executor** | RabbitMQ, Redis | 任务调度、分布式执行 |

```sql
-- 2. 链路追踪日志
CREATE TABLE trace_log (
    id BIGSERIAL PRIMARY KEY,
    trace_id VARCHAR(64) NOT NULL,
    span_id VARCHAR(64) NOT NULL,
    parent_span_id VARCHAR(64),
    service_name VARCHAR(64),
    operation_name VARCHAR(128),
    start_time TIMESTAMP,
    end_time TIMESTAMP,
    duration_ms INTEGER,
    status VARCHAR(16),
    tags JSONB,
    error_msg TEXT,
    user_id VARCHAR(64),
    create_time TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_trace_log_trace ON trace_log(trace_id);
CREATE INDEX idx_trace_log_service_time ON trace_log(service_name, create_time DESC);

-- 3. 应用运行日志
CREATE TABLE app_log (
    id BIGSERIAL PRIMARY KEY,
    trace_id VARCHAR(64),
    level VARCHAR(16) NOT NULL,  -- INFO/WARN/ERROR
    logger_name VARCHAR(256),
    thread_name VARCHAR(64),
    service_name VARCHAR(64),
    message TEXT,
    error_stack TEXT,
    user_id VARCHAR(64),
    create_time TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_app_log_trace ON app_log(trace_id);
CREATE INDEX idx_app_log_level_time ON app_log(level, create_time DESC);
-- GIN 索引支持全文检索
CREATE INDEX idx_app_log_msg_gin ON app_log USING GIN(to_tsvector('chinese_zh', coalesce(message, '')));

-- 4. LLM 调用日志
CREATE TABLE llm_call_log (
    id BIGSERIAL PRIMARY KEY,

    user_id VARCHAR(64),
    model VARCHAR(64),
    prompt TEXT,
    response TEXT,
    prompt_tokens INTEGER,
    completion_tokens INTEGER,
    duration_ms INTEGER,
    status VARCHAR(16),
    error_msg TEXT,

CREATE INDEX idx_llm_log_user_time ON llm_call_log(user_id, create_time DESC);
```

```xml
        <appender-ref ref="FILE"/>
        <appender-ref ref="DB"/>
    </root>

```

**关键类**（`LogbackDbAppender.java`）：

```java
public class LogbackDbAppender extends AsyncAppenderBase<ILoggingEvent> {
    private final List<ILoggingEvent> buffer = new ArrayList<>(1000);
    private final JdbcTemplate jdbcTemplate;

    public LogbackDbAppender(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
        // 启动定时刷盘线程
        Executors.newSingleThreadScheduledExecutor()
            .scheduleAtFixedRate(this::flush, 2, 2, TimeUnit.SECONDS);
    }

    @Override
    protected void append(ILoggingEvent event) {
        synchronized (buffer) {
            buffer.add(event);
            if (buffer.size() >= batchSize) flush();
        }
    }

    private void flush() {
        List<ILoggingEvent> toFlush;
        synchronized (buffer) {
            toFlush = new ArrayList<>(buffer);
            buffer.clear();
        }
        // 批量 INSERT 到 app_log
        jdbcTemplate.batchUpdate(
            "INSERT INTO app_log(trace_id, level, logger_name, ...) VALUES(?,?,?,...)",
            toFlush.stream().map(this::toArgs).collect(toList())
        );
    }
}
```

```sql
CREATE TABLE alert_rule (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(128) NOT NULL,
    metric VARCHAR(64) NOT NULL,         -- 监控指标（error_rate/avg_duration/...）
    operator VARCHAR(8) NOT NULL,         -- >/</>=/<=
    threshold NUMERIC,                     -- 阈值
    window_seconds INTEGER,                -- 时间窗口
    silence_seconds INTEGER DEFAULT 300,   -- 沉默期
    notify_channels JSONB,                 -- 通知渠道配置
    enabled BOOLEAN DEFAULT TRUE,
    create_time TIMESTAMP DEFAULT NOW()
);

CREATE TABLE alert_history (
    id BIGSERIAL PRIMARY KEY,
    rule_id BIGINT REFERENCES alert_rule(id),
    triggered_at TIMESTAMP,
    metric_value NUMERIC,
    message TEXT,
    notify_status JSONB,                   -- 各渠道发送结果
    create_time TIMESTAMP DEFAULT NOW()
);
```

**模板搜索 SQL 方案**：

```sql
-- 启用中文分词
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS zhparser;

-- 模板搜索表
CREATE TABLE template (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(128) NOT NULL,
    description TEXT,
    category VARCHAR(64),
    tags JSONB,
    workflow_definition JSONB,
    status VARCHAR(16),  -- draft/pending/approved/rejected
    use_count INTEGER DEFAULT 0,
    create_user_id VARCHAR(64),
    create_time TIMESTAMP DEFAULT NOW()
);

-- 全文检索索引
CREATE INDEX idx_template_name_gin ON template
    USING GIN(to_tsvector('chinese_zh', name));
CREATE INDEX idx_template_desc_gin ON template
    USING GIN(to_tsvector('chinese_zh', coalesce(description, '')));

-- 搜索 SQL
SELECT * FROM template
WHERE to_tsvector('chinese_zh', name || ' ' || coalesce(description,''))
      @@ to_tsquery('chinese_zh', '工作流 & (审批 | 自动化)')
ORDER BY ts_rank(...) DESC, use_count DESC;
```

## 十二、关于日志存储方案的说明

### 12.1 为什么选用 PostgreSQL 而非 Elasticsearch

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     选型理由                                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  1. 事务一致性                                                           │
│     • 业务数据和日志同库，可一起事务提交                                │
│     • 不会出现"日志写了但业务没成功"的情况                              │
│     • 不会出现"业务成功但日志没找到"的排查难题                          │
│                                                                          │
│  2. 架构简化                                                             │
│     • 少一个组件（ES 集群）                                             │
│     • 少一份运维（ES 调优、备份、监控）                                 │
│     • 少一份成本（ES 至少 3 节点）                                       │
│                                                                          │
│  3. PG 自身能力足够                                                       │
│     • JSONB 字段：存半结构化日志                                        │
│     • GIN 索引：JSONB + tsvector 全文检索                               │
│     • pg_trgm + zhparser：中文分词                                     │
│     • 分区表：按月分区，便于清理老数据                                  │
│                                                                          │
│  4. 性能对中等规模足够                                                   │
│     • 日增量 < 100 万条时 PG 完全扛得住                                │
│     • 全文检索在百万级数据下 < 100ms                                   │
│                                                                          │
│  5. 数据可靠性                                                           │
│     • PG 强一致，ACID 完整                                              │
│     • 主从复制、备份恢复成熟                                             │
│     • ES 是最终一致，丢失风险更高                                       │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 12.2 何时考虑引入 ES

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     引入 ES 的触发条件                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  满足以下任一条件时再考虑引入 ES：                                      │
│                                                                          │
│  • 链路追踪日志日增量 > 50 万条                                         │
│  • 全文检索成为性能瓶颈（PG 查询 > 1s）                                 │
│  • 需要长期存储（> 6 个月）且 PG 存储压力过大                            │
│  • 需要复杂的聚合分析（如多维度统计报表）                                │
│  • 需要多数据源联合分析（业务日志 + 系统日志）                            │
│                                                                          │
│  引入方式（如果需要）：                                                   │
│  • 业务关键日志继续在 PG（保证一致性）                                  │
│  • 分析型日志（链路、应用 WARN/ERROR）异步写入 ES                       │
│  • 数据流：业务服务 → Logback → 本地 + Kafka → ES                     │
│                                                  → PG（结构化）         │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 12.3 性能基准参考

```
┌─────────────────────────────────────────────────────────────────────────┐
│                 PostgreSQL vs ES（百万级数据）                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│   场景                   PostgreSQL          适用性                    │
│   ─────────────────────────────────────────────────────────────       │
│                                                                          │
│   1. 精确查询            ✅ 20-50ms          完全够用                  │
│      (execution_id)                                                       │
│                                                                          │
│   2. 范围查询            ✅ 30-100ms         完全够用                  │
│      (时间范围)                                                          │
│                                                                          │
│   3. 条件查询            ✅ 50-200ms         完全够用                  │
│      (status+time)                                                       │
│                                                                          │
│   4. 全文检索            ✅ 100-300ms        够用（加 GIN 索引）        │
│      (关键词搜索)                                                        │
│                                                                          │
│   5. 复杂聚合            ⚠️ 500-2000ms      中等规模够用               │
│      (GROUP BY 多个维度)                                                  │
│                                                                          │
│   6. 模糊匹配            ✅ 100-500ms        够用（pg_trgm）            │
│      (LIKE '%xxx%')                                                      │
│                                                                          │
│   结论：日增量 < 50 万条时，PG 完全够用，不需要 ES                       │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```
